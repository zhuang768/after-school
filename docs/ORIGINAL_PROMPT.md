# 2. 要解決的問題

畢業之後,學校帳號註冊的東西無法轉移。具體包含三類困擾:

1. 用學校信箱註冊的第三方服務帳號
2. 學校雲端硬碟裡的檔案與資料
3. 學校信箱本身的郵件與聯絡人
   而且使用者常常不知道自己當初註冊過哪些。

# 3. 現實前提(請內化進產品設計與文案)

多數服務不允許「轉移帳號擁有者」,學校雲端帳號更屬於學校。可行的做法是:**盤點出註冊過哪些、在學校信箱還能收信時把登入信箱改成個人信箱、把資料匯出備份**。產品文案不得宣稱能「轉移帳號」,要誠實說「migrate to your personal email」「export your data」。

# 4. 解法(我已決定,請不要換掉)

做成純前端、本機運作的網頁 App,三個核心功能:

- A. 帳號盤點:找出使用者用學校信箱註冊過哪些服務
- B. 引導式遷移:逐項引導把帳號改到個人信箱、備份資料,並追蹤進度
- D. 畢業倒數與提醒:依畢業日或帳號到期日安排待辦與提醒

不需要登入或帳號。所有資料只存在使用者的瀏覽器本機。

# 5. 開始前先做調查(寫入 RESEARCH.md)

- 查找現有的同類工具(信箱掃描型的帳號探索與隱私工具、帳號刪除指引目錄、各平台官方的遷移或匯出工具),列出優缺點與使用者常見抱怨,找出本產品的差異點(預期差異:完全本機處理、針對畢業情境、有時程與風險排序)
- 查證:Google 與 Microsoft 的教育版帳號在畢業後的一般政策與官方的資料匯出方式(各校設定不同,只能寫成一般性說明並提示使用者查自己學校的規定)
- 查證:Gmail 的 Takeout 匯出流程、Outlook 與 Microsoft 365 的匯出方式、各自輸出的檔案格式,決定支援哪些格式
- 查證瀏覽器 API 的支援度(檔案串流讀取、Web Worker、IndexedDB、WebCrypto),說明不支援時的降級做法
- 【新增】說明為什麼不做「直接用 OAuth 連接信箱」:授權審核負擔、安全風險與信任問題,寫進 DECISIONS.md

# 6. 方向 A:帳號盤點

## 6.1 輸入方式

1. **匯入信箱匯出檔(主要方式)**:在瀏覽器本機解析,支援 .mbox(Gmail Takeout 的輸出)與一批 .eml 檔,可含在 zip 內;其他格式依你的調查決定,不支援的要清楚說明並給出轉換建議
2. **逐項勾選服務清單**:從內建服務資料庫勾選「我可能註冊過」,適合沒有匯出檔或只想快速檢查的人
3. **手動新增**:輸入服務名稱與網址,自行建立一筆
4. 【新增】輸入「我的學校網域」(可多個):用來判斷哪些信件是寄到學校信箱;支援「學校信箱轉寄到個人信箱」的情況,依收件人標頭篩出寄給學校地址的信件

## 6.2 本機解析引擎(核心技術難點)

- 必須在 Web Worker 中以串流方式處理,**能處理數 GB 的 mbox 而不凍結介面、不爆記憶體**,並顯示即時進度、可取消
- 只擷取必要欄位:寄件者、收件者、日期、主旨、列表退訂標頭、必要時信件開頭一小段文字;**不保存完整信件內容**。解析完成後原始檔案內容立即釋放
- 把信件分類為:歡迎或註冊確認、驗證碼或驗證連結、密碼重設、收據或帳單、安全警示、行銷與電子報;依分類與出現頻率給出「這很可能是你的帳號」的信心等級(High / Medium / Low),文字上一律說「likely」,不得宣稱確定
- 以可註冊網域(使用公共後綴清單)正規化寄件者,合併同一服務的多個寄件網域與子網域;對應到內建服務資料庫,未知者列為「Unrecognized service」並提供手動歸類
- 每個服務顯示:名稱、信心等級、首次與最近出現日期、相關信件數量、判斷依據(例如「Welcome email on 2022-09-03」)。信件主旨等敏感文字預設只在當次畫面顯示,可選擇不保存
- 【新增】判斷「這個帳號是不是用學校信箱」的證據要清楚,避免把一般電子報當成帳號;提供使用者逐項確認或排除(Mine / Not mine / Not sure)
- 安全:信件內容一律當純文字處理,**絕不渲染信件中的 HTML、不載入任何遠端圖片或連結**;限制檔案大小、巢狀壓縮與解壓縮比例,防止壓縮炸彈與惡意檔案

## 6.3 內建服務資料庫(Service Catalog)

- 內建一份精選、經你逐項查證的服務清單,至少 40 筆,涵蓋:雲端儲存、開發工具、設計與創作工具、生產力與筆記、學習與課程平台、串流與娛樂、學生優惠相關服務、購物與金融、校園相關(例如課程管理系統、視訊會議、圖書館)。**品質優先於數量**:查證不了的就不收錄
- 每筆欄位:名稱、分類、網域列表、官方「更改登入信箱」說明連結與簡要步驟、官方資料匯出連結或步驟、是否有學生或教育方案以及信箱變更對優惠的影響(需查證)、帳號是否可刪除、最後確認日期、來源連結
- 資料放在版本化的 JSON,附結構定義與驗證測試;提供腳本檢查所有連結是否仍有效,供日後維護
- 提供 CATALOG_GUIDE.md:如何新增、查證與更新一筆服務

# 7. 方向 B:引導式遷移

## 7.1 任務模型

盤點結果與勾選結果都轉成「任務」。每個任務有:

- 類型:Change login email / Export data / Replace with alternative / Delete account / Check recovery email
- 狀態:Not started / In progress / Done / Can't migrate / Not mine
- 風險等級與優先序(見 7.2)
- 備註欄位,與可勾選的子步驟

## 7.2 風險排序(讓使用者知道先做哪個)

依下列因素計算優先序並顯示理由:

- 是否可能涉及金流(有收據或帳單信件)
- 資料重要性(雲端儲存、程式碼託管、設計與文件類)
- 不可逆性(該服務不允許更改信箱)
- 學生優惠是否會失效
- 【新增】**帳號救援風險**:學校信箱是否可能同時是其他帳號的救援信箱(例如密碼重設信),這類帳號失去學校信箱就可能鎖死。提供「Recovery email check」引導,逐項檢查使用者最重要的帳號(例如主要個人信箱、銀行、社群)的救援信箱設定
- 演算法必須確定性,規則寫在 Methodology 頁面,讓使用者看得懂也可以調整

## 7.3 逐項引導

- 每個服務一頁:為什麼重要、風險、步驟(依第 6.3 查證過的內容)、官方連結(以新分頁開啟,並檢查網域)、完成後的確認清單
- 通用備援引導:服務不在資料庫時,如何尋找更改信箱的設定位置、如何聯絡客服,並提供可一鍵複製的英文客服訊息範本(例如請求更改帳號信箱或匯出資料)
- 安全提醒貫穿全程:**本產品永遠不會要求使用者輸入任何密碼**,也不儲存憑證;提醒遷移時一併開啟雙重驗證並更新救援方式;連結只指向官方網域

## 7.4 學校提供的資料遷移(第二、三類困擾)

以任務形式提供引導,不直接串接學校系統:

- 學校雲端硬碟:盤點(哪些檔案與共享資料夾)、官方匯出方式、改為共享給個人帳號或下載備份的取捨,並提示「各校設定不同,請以學校資訊單位說明為準」
- 郵件與聯絡人:匯出方式、設定轉寄或存檔的選項與限制、通知重要聯絡人新信箱的範本訊息
- 使用者可輸入「我的學校的規定」(例如帳號保留多久、是否提供校友信箱、聯絡窗口),系統將其用於倒數計算與提醒
- 所有一般性說明來自你查證的官方文件,標註日期與來源

## 7.5 進度儀表板

- 顯示總體完成度、高風險待辦、已完成清單,並隨狀態更新有流暢的動畫回饋
- 可匯出為「Migration report」:一份可列印的 PDF 或文字摘要,列出所有帳號、狀態與備註(本機產生)

# 8. 方向 D:畢業倒數與提醒

- 輸入畢業日與「學校帳號預計停用日」(可選,未知時由使用者選擇學校常見的保留期限或自填,並明確標示是假設)
- 依剩餘時間與任務優先序,自動排出時間表(例如倒數各階段該完成哪些事),並提供「Today」視圖:今天該做什麼、逾期了什麼
- 提醒方式要誠實且可靠:
  - 匯出為行事曆檔(.ics)含提醒,匯入 Google、Apple 或 Outlook 行事曆;這是主要的可靠方式
  - 網頁開啟時的畫面內橫幅與徽章
  - 若使用瀏覽器通知,必須在介面說明「分頁關閉時可能收不到」,不可誇大
- 【新增】**「Already expired」模式**:若帳號已被停用,引導使用者的補救路線:聯絡學校資訊單位詢問是否可暫時恢復或匯出資料、檢查是否有校友信箱方案、用其他救援信箱嘗試帳號復原、對各服務使用客服訊息範本請求變更信箱,並說明哪些資料可能已無法取回,誠實管理期望
- 【新增】倒數過程中,依使用者行為動態調整待辦(完成後自動往後推進,逾期自動提高優先序)

# 9. 技術要求

- 純前端單頁網頁 App,無後端,無使用者帳號;靜態託管(免費方案即可),可安裝為 PWA 並可離線使用
- 建議:TypeScript + React(Vite 建置),本機儲存用 IndexedDB(搭配成熟的輕量封裝),解析引擎在 Web Worker;可替換並說明
- 【新增】可選的本機加密:使用者可設定密碼,以 WebCrypto 加密保存在本機的資料(P1);忘記密碼無法復原,必須在介面誠實說明
- 【新增】嚴格的內容安全政策:不載入任何第三方腳本,**不含分析、追蹤或廣告程式**;除了使用者主動點擊開啟的官方連結與資料庫更新檢查(若有,說明並可關閉)之外,**不發出任何網路請求**
- 提供「Delete all my data」一鍵清除,與整個工作區的匯出與匯入(JSON)
- 無障礙達到 WCAG 2.2 AA:鍵盤可操作、螢幕閱讀器可用、對比充足、尊重減少動態偏好
- 響應式,手機與桌面都好用(匯入大檔案的流程要考慮手機限制並給出清楚提示)
- 依賴越少越好,每個第三方套件說明用途與授權

# 10. 視覺與動態設計

- 先做設計研究:參考優秀的資訊設計、進度與清單類產品、安全與隱私類產品的介面,以及設計社群的案例;把參考了哪些、學到什麼寫進 DESIGN.md。只借鏡手法,不可複製他人的素材、文案或程式碼
- 不要有「AI 範本感」:避免無個性的紫藍漸層、到處用 emoji 當圖示、千篇一律的卡片版型、預設字體加預設圓角
- 建立自己的設計系統:色彩、字體、間距、圖示風格統一;氣質要「冷靜、可信、讓人安心」,不要用警告紅色製造焦慮
- 動態效果:掃描時帳號逐一浮現的動畫、風險排序與狀態變更時的流暢重排、進度環與完成回饋、轉場;有節奏與緩動,尊重減少動態設定
- 首次進入的畫面要在 10 秒內讓人明白「這個工具做什麼」以及「我的資料不會離開我的裝置」,並提供一個內建的示範資料模式,讓人不用匯入真實信箱就能體驗完整流程

# 12. 驗收測試(實際執行並寫入 TEST_REPORT.md)

- 解析引擎:使用**自行產生的合成信箱檔案**(絕不使用真實個人資料)測試各種分類、多語言主旨、損毀信件、巨大附件、超長標頭、惡意檔案(壓縮炸彈、惡意 HTML);評估分類的準確率與召回率並記錄方法與結果
- 大檔測試:合成一個數百 MB 以上的 mbox,驗證串流處理不凍結介面、記憶體使用穩定,並記錄量測數據(不得捏造)
- 隱私驗證:自動化測試在整個掃描與遷移流程中**沒有任何對外網路請求**(用端到端測試工具監看網路並斷言)
- 服務資料庫:結構驗證、網域不重複、所有外部連結有效、每筆都有最後確認日期與來源
- 風險排序與時間表:黃金測資、邊界情況(已過期、畢業日已過、沒有任何帳號)
- 端到端:匯入示範信箱 → 看到帳號清單 → 確認與排除 → 產生任務與時間表 → 逐項完成 → 匯出 .ics 與 Migration report
- 離線:安裝為 PWA 後離線完成一次完整流程
- 無障礙:自動化檢測加人工鍵盤與螢幕閱讀器抽測
- 跨瀏覽器:主要的桌面與行動瀏覽器,並記錄不支援的功能與降級行為
- 誠實列出已知限制(Known Limitations),特別是:信箱分類只是「可能」、服務步驟可能隨官方更新而過時、各校政策不同

# 13. 工作方式與品質門檻

- 每個階段有「完成定義」:可建置、無錯誤、該階段功能實測通過、文件已更新
- 小步提交,提交訊息清楚;嚴格型別與程式碼檢查,零警告交付
- 建議階段:調查與查證 → 解析引擎與合成測資 → 服務資料庫 → 任務與風險排序 → 引導與備援 → 倒數與提醒 → 介面與動態 → 隱私與無障礙強化 → P1 → P2 → 全面測試與修正 → 部署與文件
- 若進度落後:先砍 P2,再砍 P1,絕不犧牲隱私承諾、解析引擎的穩定性與服務資料的正確性
